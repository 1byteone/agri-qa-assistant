2.1 智能体核心认知与体系架构 
2.1.1 智能体的核心定义与核价值 
智能体（Agent，也常称为 AI Agent）是人工智能领域中能够感知环境、自主决策、执
行动作并优化结果以实现预设目标的自主系统。它突破了传统大型语言模型（LLM）“只
说不做”的局限，通过 “感知 - 思考 - 行动 - 观察” 的闭环，将 AI 能力从 “文本生成”升
级为 “任务执行”，成为连接 AI 与现实世界的核心载体。 
原生 LLM 仅能依托训练数据集完成被动文本输出，不存在自主思考、外部操作的能力，
天然存在知识滞后、幻觉编造的缺陷；基础 Chain 链路需要开发者提前写死全部执行流程，
无论用户提问如何变化，都只能机械执行预设步骤，无法适配模糊、多目标的复杂需求。
而 LangChain 智能体依托 ReAct 推理行动机制，完整实现 “思考决策—工具执行—结果观
察—迭代优化” 的循环流程，能够自主拆解任务、筛选外部资源，从根源弥补原生大模型
与固定链路的各项短板，实现真正的自主智能交互。 
一句话总结：AI 智能体能够自主感知外部环境、解析用户自然语言目标、自主推理执
行逻辑、主动调用外部工具、接收环境反馈迭代、输出标准化合规结果的智能化执行系统。 
2.1.2 智能体的四大核心特征 
完整工业级可投入使用用的LangChain 智能体必须同时具备四大核心特征，这也是区
分普通LLM 问答、固定脚本与标准智能体的判定依据，四项缺一不可： 
（1）自主性（Autonomy）：无需人工分步干预任务流程，智能体可基于用户目标与
当前环境信息自主判断 “需要做什么、以何种顺序完成”，自主筛选适配工具、拆分子任务、
规划完整执行路径，全程不需要开发者预设全套执行脚本，独立走完完整任务闭环。 
（2）交互性（Interactivity）：支持双向动态交互能力，智能体可同时对接用户输入、
本地文档、第三方网络 API、内存存储等多类内外资源，接收工具、用户的反馈信息后，
动态调整后续推理与执行策略，不会机械重复固定操作。 
（3）目标导向性（Goal-Oriented）：智能体全部思考、执行动作都围绕用户核心需求
展开，内置复杂任务拆解逻辑，能够自动区分有效步骤与无效冗余操作，对子任务划分优
先级，优先完成贴合用户目标的执行流程，杜绝无意义循环调用。 
（4）适应性（Adaptability）：依托内置记忆系统留存全部交互经验，能够适配残缺提
问、模糊口语、场景变更等各类不确定输入，不会单一、机械地套用同一套应答逻辑，可
根据对话上下文灵活调整推理思路。 
2.1.3 智能体主流分类与适配场景 
根据智能体的记忆能力、决策逻辑、应用复杂度，行业将智能体划分为六大主流类型，
结合本课程智能搜索开发主线，课堂实训以目标导向智能体、学习型智能体为核心讲解对
象，其余类型作为拓展理论补充。 
（1）反应式智能体（Reactive Agent）：无记忆模块，仅依据当前单次输入即时给出
响应，逻辑极简、响应速度快，适配工业设备监控、固定单指令应答等轻量化场景，不存
在多轮对话交互能力。 
（2）基于模型的智能体（Model-Based Agent）：内置环境状态模拟逻辑，可预判工具
调用、外部接口返回的结果变化，适配输入动态变化的交互场景，能够根据预判调整工具
调用顺序。

（3）目标导向智能体（Goal-Based Agent）：以用户明确任务目标为核心，原生支持
复杂任务分层拆解，是商用智能问答、私有知识库检索系统的主流实现类型，本课程天气、
知识库工具案例均基于该类型开发。 
（4）效用函数智能体（Utility-Based Agent）：引入成本、优先级、容错率等量化评估
规则，可在多条可行执行路径中筛选最优方案，适配资源分配、多维度方案对比等优化类
场景。 
（5）学习型智能体（Learning Agent）：依托长期记忆存储历史交互数据，每一轮对
话后自动优化自身决策逻辑，交互次数越多应答精准度越高，适配长期个性化交互项目。 
（6）多智能体系统（Multi-Agent System）：由多个功能差异化智能体分工协作，分
别负责检索、计算、文案生成等细分模块，适配智慧城市、大型数据分析等超复杂工程项
目。 
2.1.4 智能体完整架构与运行闭环 
LangChain 体系下所有标准智能体统一遵循五层分层架构，五层模块层层联动、数据
双向流转，共同支撑 “感知 - 记忆 - 推理 - 规划 - 执行” 的完整自主运行闭环，各层级权责完
全解耦，可单独替换、灵活组合。 
（1）感知层：核心功能为全量信息采集与标准化封装，统一接收用户自然语言提问、
工具返回原始数据、历史对话记录等全部输入内容，将各类零散信息转换为 LangChain 标
准化消息对象，向下传递至记忆层与推理层，是智能体所有输入信息的统一入口。 
（2）记忆层：负责全部交互数据的存储与调取，分为短期会话内存记忆、Redis 长期
持久化记忆两类，完整留存对话上下文、工具执行中间结果，保障多轮连续提问时，智能
可读取历史内容连贯作答，是智能体适应性特征的底层支撑。 
（3）推理层：智能体的核心决策大脑，载体为 LLM 大模型，依托 ReAct 机制完成语
义理解、需求拆解、工具匹配、参数生成全部推理工作，接收感知层、记忆层传递的消息
后，输出下一步行动指令。 
（4）规划层：负责复杂任务调度，接收推理层的核心目标后，将单一复杂需求拆分为
有序子任务，划分各子任务执行优先级，避免无序重复调用工具，简化推理层的决策负担。 
（5）执行层：承载所有外部操作，由各类自定义 Tool 工具集合组成，接收规划层下
发的行动指令，完成网络请求、文档读取、数值计算等具象操作，执行完成后将结果封装
为工具消息，反向回流至推理层，形成迭代闭环。 
智能体标准化完整工作闭环完整流转流程：用户输入自然语言请求进入感知层 — 感知
层将内容封装为标准化消息 — 记忆层读取当前会话全部历史消息补充上下文— 推理层结
合系统提示、历史消息完成自主推理，判断是否需要调用工具、调用哪一款工具、传入对
应参数 — 执行层运行指定工具获取外部原始数据，生成工具消息 — 工具消息回流至推理
层，模型整合全部消息二次推理，判断信息是否充足— 信息充足则生成标准化应答，存入
记忆层并对外输出；信息不足则再次发起工具调用循环。全程无需人工介入，完整实现自
主闭环执行。

2.2.2 消息与提示词 
1、什么是提示词 
提示词（Prompt）是连接开发者、用户与大模型的核心交互媒介，是AI 可控开发的第
一核心要素，没有标准化提示词，模型输出将完全随机、不可复用、无法落地工程场景。
其核心作用可总结为四大核心价值： 
 角色定义：赋予模型专属身份与能力边界，明确模型可以做什么、禁止做什么，从
根源约束模型行为，杜绝无效输出与幻觉内容。 
 任务指令：清晰传递用户核心需求、任务目标、执行步骤，解决模型语义理解偏差、
需求拆解错误的问题。 
 格式约束：统一输出格式、排版规范、内容长度，让模型自由文本转化为标准化可
复用内容，适配项目开发。 
 逻辑引导：引导模型遵循固定推理逻辑、思考步骤，提升答案精准度、逻辑性，适
配复杂任务执行。 
如【例2.1-1】的提示词： 
你是专业的Python 编程助教。 
【强制硬性规则，绝对不可违反】 
1. 只允许回答Python 编程、代码语法、Python 实操相关问题 
2. 所有非Python 相关问题，必须直接固定回复：抱歉，我仅可解答Python 基础编程
问题，不支持该类需求。 
3. 禁止强行作答、禁止跨界创作、禁止自作主张回答无关内容 
【例2.1-2】的提示词： 
你是专业天气预报助手，仅可调用get_weather_for_location工具查询城市天气，严格遵
循规则： 
1. 用户询问任意城市天气，必须调用工具获取实时数据，禁止编造气温、天气状况； 
2. 工具返回结果后，按照指定结构化格式整理输出； 
3. 无对应城市数据如实告知，禁止虚构天气信息； 
4. 可结合上下文记忆回答用户追问。 
可用工具：get_weather_for_location（输入中文城市名，返回近3 天分段天气） 
提示词是零成本优化模型效果的核心手段，无需微调模型、无需算力投入，仅通过话
术优化即可大幅提升智能体精准度、可控性、稳定性。 
2、什么是消息 
（1）消息定义 
消息是 LangChain 框架中和 LLM 交互的最小标准化单元，每条消息固定包含角色标识、
文本内容、交互元数据三部分，区分对话来源，是提示词的标准化承载容器。普通纯文本

--- Page 12 ---
 
 
字符串无角色区分，无法留存多轮上下文；而结构化消息可精准划分系统、用户、AI、工
具四类对话身份，支撑完整多轮交互记忆。 
（2）消息与提示词从属关系： 
在 LangChain 及大语言模型（LLM）的交互体系中，提示词（Prompt） 和消息
（Message） 是紧密关联但层次不同的概念，二者的关系可以概括为：消息是承载提示词
的结构化载体，提示词是消息中传递给模型的核心指令内容。 
 提示词（Prompt）：传递给模型的指令、问题、上下文信息的总和。明确模型的任
务目标，引导模型生成预期输出。如自然语言文本（写一篇关于 AI 的短文）。 
 消息（Message）：LangChain/LLM 交互中标准化的通信格式，包含角色、内容等
元数据，区分对话角色（用户 / 工具 / 系统），携带上下文历史，让模型理解对话
逻辑。如结构化对象（HumanMessage/AIMessage）。 
提示词是写入消息内部的指令文本，消息是承载提示词的结构化外壳；一段提示词不
能脱离消息单独实现角色区分，一条消息内部必然包含对应提示内容。在 LangChain 的对
话式交互中，用户输入的提示词会被封装成 HumanMessage，而模型的输出会被封装成 
AIMessage。

AIMessage 元数据中的Token 是AI 认识世界的最小“文字碎片”。就像我们人类学语
言要先认识字一样，AI 大模型看不懂完整的句子，它只能看懂被切碎后的“最小意义单

绕 Token 展开。 
举个具体的例子： 
英文单词 “unhappiness”可能被拆成 ["un", "happi", "ness"] 三个Token 
中文句子 “今天天气真好”可能被拆成 ["今", "天", "天", "气", "真", "好"] 六个Token

大约会消耗1500~2000 个Token。

合要求的 AIMessage 到历史里，模型后续会参考这条 “假回复”的风格 / 内容，输出更符
合预期的结果。例如：

入输出逻辑围绕结构化的消息对象展开：它接收由多条不同角色的消息组成的列表作为输

具体来说，输入的消息列表并非简单的文本拼接，而是包含了明确角色标识的结构化

务的完整上下文。 
而模型输出的 AIMessage 同样是结构化对象，不仅包含核心的文本回复内容，还可携
带额外元数据（如生成时间、令牌消耗、工具调用意向等），既可以直接作为最终结果返
回给用户，也能作为历史消息再次传入模型，实现多轮对话的连贯流转。 
2.2.3 大语言模型 
1、什么是大语言模型 
大语言模型（LLM）是智能体的推理引擎，它们驱动智能体的决策过程，确定调用哪
些工具、如何解释结果以及何时提供最终答案。大语言模型的功能除了文本生成，许多模
型还支持： 
  工具调用：调用外部工具（如数据库查询或 API 调用）并在其响应中使用结果。 

--- Page 18 ---
 
 
  结构化输出：模型响应被限制为遵循定义的格式。 
  多模态：处理和返回除文本之外的数据，例如图像、音频和视频。 
  推理： 模型执行多步推理以得出结论。

1、典型智能体的整体运行流程 
典型智能体将大语言模型与工具结合，创建能够对任务进行推理、决定使用哪些工具
并迭代地解决问题的系统。图2.3-1 是一个典型的智能体的整体运行流程示意图，展示了一
个基于 “感知 - 决策 - 执行”逻辑的系统运行过程： 
 
图2.3-1：典型的智能体的整体运行流程 
运行流程拆解说明： 
（1）request（用户请求） 
流程起始输入项，由用户输入自然语言问题、业务任务构成，会统一封装为标准化 
HumanMessage 消息，作为整个智能体循环的初始输入源。 
（2）model（大模型推理核心） 
智能体的决策大脑，同时接收当前用户请求与 memory 存储的全部历史对话消息；结
合系统提示完成语义理解、任务判断、路径规划，自主生成下一步行动指令：若无需外部
数据则直接生成最终应答，若需要实时外部信息则输出工具调用指令 action。 
（3）memory（对话记忆存储模块） 
智能体上下文存储载体，双向对接模型：一方面接收 model 产生的所有消息（用户提
问、AI 回复、工具返回内容）并持久保存；另一方面在每一轮推理前，向 model 推送完整
历史交互数据，为模型决策提供上下文支撑，实现连贯多轮对话。 
（4）tools（外部工具执行集） 
承接模型下发的 action 行动指令，是智能体获取外部实时数据、执行实操动作的执行
单元。当模型判断需要外部信息或执行特定动作时，就会调用工具（比如数据库查询、计
算器、API 调用等）。工具执行完毕后，将原始返回数据封装为 observation 观测信息回传
给模型，补充推理所需外部真实信息。 
（5）result（标准化输出结果） 
当 model 整合用户提问、历史记忆、工具观测数据，判定信息充足时生成最终结构化
应答，对外反馈给用户；同时本次完整交互的全部消息统一存入 memory 留存，观测信息
同步回传模型，完成一轮完整执行闭环。

import datetime 
from langchain.agents import create_agent 
from langchain.tools import tool 
 
# 工具1：实时日期获取工具（解决模型知识滞后） 
@tool 
def get_current_datetime() -> str: 
    """ 
    获取当前系统标准北京时间，包含年月日、星期 
    用于回答所有时间、日期、年份相关提问 
    返回：标准化格式化时间字符串 
    """ 
    week_list = ["星期一","星期二","星期三","星期四","星期五","星期六","星期日"] 
    now = datetime.datetime.now() 
    week = week_list[now.weekday()] 
    return f"当前时间：{now.strftime('%Y 年%m 月%d 日')} {week}" 
 
# 工具2：文本字数统计工具（自定义业务工具） 
@tool 
def text_word_count(text: str) -> str: 
    """ 
    统计输入文本的有效字数（不含空格、换行） 
    参数：text - 需要统计的原始文本字符串 
    返回：文本有效字数统计结果 
    """ 
    if not text: 
        return "输入文本为空，无法统计字数" 
    clean_text = text.replace(" ","").replace("\n","") 
    return f"文本有效字数为：{len(clean_text)}字" 
 
# 系统规则约束（最高优先级） 
SYSTEM_PROMPT = """ 
你是多功能实用助手，严格遵循以下规则： 
1. 时间、日期提问必须调用get_current_datetime 工具，禁止编造时间 

--- Page 25 ---
 
 
2. 字数统计需求必须调用text_word_count 工具，精准计算 
3. 非工具类问题直接自主回答，简洁精准、无冗余内容 
4. 杜绝AI 幻觉，所有工具数据如实反馈 
""" 
 
# 组装多工具智能体 
agent = create_agent( 
    model=llm, 
    tools=[get_current_datetime, text_word_count],

2.3.2 Tools 工具 
大语言模型的知识全部来源于训练阶段的数据集，模型固化的训练数据存在时间截止
点，无法获取实时、动态外部信息，也不能主动执行各类程序操作。想要突破模型自身能

工具机制的核心逻辑是由大模型自主判断需求，主动调用外部 API、本地函数、第三
方服务，获取真实外部数据并交给模型整合分析，以此弥补模型静态知识库的短板。

（1）连接各类外部资源：可访问数据库、实时公开 API（天气、日期、股票等）、本
地文本文件、网页文本； 
（2）执行实体操作任务：运行 Python 计算代码、发送 HTTP 网络请求、调用计算

2.3.3 Memory 记忆 
记忆是 LangChain 智能体用于存储全部历史交互信息的存储系统。对 AI 智能体而言，
记忆是实现连贯多轮对话的核心基础：智能体可读取过往问答内容理解上下文、根据用户
历史交互适配回答风格、从多轮反馈中调整输出逻辑。当智能体处理多轮连续提问、复杂
分步任务时，记忆能力直接决定交互流畅度与用户体验。 
LangChain记忆系统模拟人类记忆模式，分为短期会话记忆与长期持久化记忆两大类： 
 
短期记忆（临时内存记忆）：仅保存在程序内存中，仅在单条会话线程内生效；
程序关闭、服务重启后所有对话记录全部丢失，适合单次调试场景。 
 
长期记忆（持久化存储记忆）：将对话、用户关键信息持久存入数据库，支持跨
程序重启、跨会话检索历史交互内容，适用于线上生产部署场景。 
1、短期内存记忆 InMemorySaver 
短期记忆依托InMemorySaver 实现，存储介质为程序运行内存。使用规则： 
（1）创建智能体时必须传入checkpointer=InMemorySaver()开启记忆。 
agent = create_agent( 
    checkpointer=InMemorySaver(),   
) 
（2）LangChain 记忆基于线程隔离，调用agent.invoke()时必须配置唯一thread_id 线程
标识。同一thread_id 下的所有对话消息会自动存入内存，实现上下文连贯读取，不同
thread_id 会话完全隔离，无法互相读取历史对话。 
agent.invoke(

2、长期持久化记忆 RedisSaver 
短期内存记忆存在明显短板：程序重启、会话结束后所有对话记录直接丢失，无法留
存长期用户交互数据。长期记忆通过数据库持久化存储对话检查点，并能通过检索召回。 
1）核心原理 
长期记忆的核心原理是存储与检索： 
（1）将用户的关键信息 / 历史对话嵌入为向量，存储到向量数据（可以基于Redis、
MongoDB、PostgreSQL 等数据库来保存聊天记录 ）； 
（2）新对话时，检索向量库中与当前问题相关的长期记忆； 
（3）将短期上下文 + 检索到的长期记忆一起传入大语言模型。 
2）长期记忆的实现方式 
长期记忆存储方案推荐使用Redis-stack 数据库实现持久化会话记忆。Redis 8.0 及以上
版本支持向量结构，可存储对话向量、会话检查点数据，具备亚毫秒级读写延迟，支持实
时对话 AI、推荐系统等高实时性业务场景。 
（1）RedisSaver 类

2.3.4 结构化输出 
在 AI 应用开发场景中，大语言模型（LLM）原生输出内容为无规范约束的非结构化自
然语言。若直接将这类文本用于程序逻辑处理，例如数据入库、接口参数传递、工具函数
调用等场景，需要额外编写文本解析逻辑，不仅开发效率低下，还极易出现解析异常、数
据错乱等问题。 
LangChain 提供了一套成熟完整的结构化输出解决方案，可约束智能体按照开发者指
定、格式可预测的标准返回数据。开发者无需手动编写自然语言解析代码，可直接获取 
JSON 字符串、Pydantic 模型实例、数据类等标准化结构化数据，可直接在业务程序中读取、
运算、存储。 
1、Pydantic 模型基础 
Pydantic 是 Python 生态中用于强类型数据校验、结构化数据定义的工具库，同时也是 
LangChain 实现高精度结构化输出的底层核心依赖。 
其核心作用是预先定义数据规范：包含字段名称、数据类型、数值、文本约束规则，
同时自动对输入输出数据执行合法性校验，完美适配 LLM 标准化输出的业务需求。 
对于编程初学者，可将 Pydantic 模型理解为三层能力载体： 
（1）标准化数据说明书：强制规定数据必须包含的全部字段、每个字段对应数据类型
（数字 / 字符串 / 列表等）、字段约束条件（例如价格数值必须大于 0）； 
（2）全自动数据校验器：自动校验数据是否匹配预设规范，不合规数据直接抛出异常；
同时支持自动类型转换，例如自动将字符串"9999"转换为数字9999； 
（3）便捷结构化数据容器：数据校验通过后，会生成模型实例对象，可直接通过.属
性访问字段（如obj.price），相比原生字典语法更简洁直观。

2.4.2 三类流式输出模式 
流式传输是构建高响应 AI 应用的核心能力。借助分片实时输出，无需等待完整响应生

分别适配实时打字、工具进度日志、Agent 执行流程监控三大场景。 
1、LLM Token 流式输出 
（1）核心原理 
大模型生成文本时不会等全部内容生成完毕再统一返回，每生成一组 Token 就实时通

stream_mode="messages"。

2.5 表达式语言 
2.5.1 表达式语言基础 
1、核心概念 
LangChain 中的表达式语言LCEL（LangChain Expression Language）是 LangChain 核心
的链式调用语法（Chain）。它是一种组件组合范式，通过管道符“ |” 将多个独立的功能
组件（如 Prompt、LLM、Parser、Tool、Memory 等）串联成一个可执行的“流水线”，让
数据自动从左到右流经每个组件完成处理，无需手动分步传递中间结果。 
2、链式调用 
可以把链式调用理解为：你要做一道菜（完成一个 AI 任务），需要经历 “备料→烹
饪→装盘” 三个步骤，链式调用就是把这三个步骤固定成一条自动化生产线，你只需放入
原材料（输入数据），就能直接拿到做好的菜（最终结果）。 
在 LangChain 中： 
 组件 = 生产步骤（备料 / 烹饪 / 装盘）； 
 管道符 | = 生产线的传送带； 
 输入数据 = 原材料； 
 最终结果 = 做好的菜。 
1） 通用格式：组件1 | 组件2 | 组件3 | ... 
chain = 组件A | 组件B | 组件C 
用 | 串联组件时，必须保证前一个组件的输出就是后一个组件的输入。 
2）执行调用 
（1）同步调用 
content= chain.invoke(输入数据) 
print(content) 
（2）流式输出 
for chunk in chain.stream(输入数据): 
    print(chunk,end="",flush=True) 
3、解释器 
LangChain 解析器的核心作用是将大语言模型（LLM）返回的非结构化文本，转换成
结构化的数据（如字典、列表、Pydantic 模型等），让你能直接用代码处理模型输出，而
不用手动写字符串处理逻辑。 
1）简单解析器 
StringOutputParser 是最基础的解析器，仅将模型输出转为纯字符串，适合不需要结构
化的场景。 
2）结构化解析器 
JsonOutputParser 是将模型输出转为 JSON 格式（Python 字典），适合需要提取多字段
信息的场景（如提取作物名称、病虫害、风险等级）。 
3）强类型解析器、 
PydanticOutputParser 是基于 Pydantic 模型定义输出结构，强制模型输出符合格式的内
容，还能自动校验字段类型，适合生产环境。

2.5.2 Runnable 组件 
Runnable 是 LangChain 框架的核心抽象，简单来说，所有能被管道（|）串联的组件，

--- Page 51 ---
 
 
本质上都是 Runnable。它定义了统一的接口（invoke()/stream()/batch()），让不同功能的组
件（提示词、模型、工具、解析器等）能像 “乐高积木” 一样灵活组合，这也是“|”语
法构建调用链的底层基础。 
1、Runnable 核心作用 
1）统一接口：无论是什么组件（模型、提示词、自定义函数），只要实现 Runnable 
接口，就拥有 invoke()（单次调用）、stream()（流式输出）、batch()（批量调用）方法； 
2）管道兼容：只有 Runnable 组件才能用 “| ”语法串联，保证“前一个输出就是后一
个输入” 的流畅衔接； 
3）状态隔离：每个 Runnable 都是独立的，调用时互不干扰，便于调试和复用。 
2、常用 Runnable 组件类型 
LangChain 内置了大量开箱即用的 Runnable 组件，主要包括以下几类： 
1）基础 Runnable 组件 
这些组件是内置组件，无需手动封装，实现了 Runnable接口。即直接用“| ”串联的都
是Runnable。 
 提示词模板：BaseChatPromptTemplate 
 聊天模型：BaseChatOpenAI 
 解析器：BaseOutputParser 
2）自定义 Runnable 组件 
（1）RunnableLambda 
这是最常用的自定义方式。 将普通函数封装为 Runnable，适配管道语法。

def save_image(images: Images) -> Images: 
    """ 
    下载远程图片保存至本地，替换URL 为本地文件路径 
    参数： 
    images: Images 图片输入模型 
    返回： 
    Images 图片输出模型  
    """ 
    paths = [] 
    for i, url in enumerate(images.urls): 
        file_name = f"{images.timestamp}_{i}.png" 
        file_path = f"./{file_name}" 
        img_response = requests.get(url) 
        img_response.raise_for_status() 
        with open(file_path, "wb+") as f: 
            f.write(img_response.content) 
        paths.append(file_path) 
    return Images( 
        prompt=images.prompt,  
        size=images.size,       
        n=images.n, 
        urls=paths,  
        timestamp=images.timestamp 
    )

本项目搭建一套面向农业领域的智能问答原型系统，支持多轮对话记忆、私有知识库

（1）全异步架构：异步接口搭配智能体异步流式输出，资源利用率高，响应速度快； 
（2）成熟流式交互：基于标准 SSE 实现打字机效果，交互体验接近主流大模型对话

4、现存不足与优化方案 
（1）知识库模块 
现状：私有知识库采用硬编码字典存储，仅简单字符串匹配，无法承载大量文档，不
支持 PDF、文档文件导入。

async def stream_generator(question: str, session_id: str): 
    """流式生成器""" 
    try: 
        logger.info(f"开始处理问题: {question}") 
        async for item in agri_stream_chat(question, session_id): 
            # 序列化为标准JSON 字符串 
            json_str = json.dumps(item, ensure_ascii=False) 
            yield f"data: {json_str}\n\n" 
            logger.info(f"发送: {item.get('type', 'unknown')}")

        import traceback

            "type": "error", 
            "chunk": f"处理失败: {str(e)}" 
        } 
        yield f"data: {json.dumps(error_data, ensure_ascii=False)}\n\n"
