# CropWise 场景化产品开发设计

**版本**：0.1（场景入口 MVP）  
**日期**：2026-08-09  
**产品定位**：面向江西种植者、农技人员和江农师生的证据优先农业决策工作台

## 1. 竞品研究结论

本轮核验了竞品官网和公开机构资料。以下是产品页面明确表达的能力，不把宣传数字当作事实：

| 产品/资料 | 已验证的产品重点 | CropWise 的机会 |
| --- | --- | --- |
| [Plantix](https://plantix.net/en/) | 免费作物诊断、处理建议和农技知识 | 诊断之外增加地区/生育期/复查闭环，避免“一张图直接确诊” |
| [PlantVillage](https://plantvillage.psu.edu/) | 面向小农户的作物知识、社区和气候适应内容 | 把开放知识转成江西农时和田间行动方案 |
| [Farmer.Chat](https://farmer.chat/) | 文字、语音、照片、多语言的免费农技助手 | 以可信证据、来源链和农技转交格式建立信任 |
| [Wadhwani AI](https://www.wadhwaniai.org/) | 面向农业等公共服务的负责任 AI 项目 | 明确风险边界、人工复核和可审计记录 |
| [xarvio](https://www.xarvio.com/) | 作物健康、病害风险、田块/分区级数字农业工具 | 先做低门槛的场景简报，再逐步接入田块和时序数据 |
| [CropX](https://cropx.com/) | 传感器、土壤和灌溉决策的农场管理系统 | 不复制硬件，先用问答和知识库完成轻量决策支持 |
| [Taranis](https://www.taranis.com/) | 高分辨率田间图像、作物管理和精准农业 | 图片作为辅助证据，结合文本和复查结果，不把视觉结果当确诊 |
| [John Deere Operations Center](https://www.deere.com/en/technology-products/precision-ag-technology/operations-center/) | 连接田块、机器和操作员数据，支持农场决策 | 建立“问题 - 行动 - 复查”事件时间线，未来接入农机数据 |
| [FAO Digital Agriculture](https://www.fao.org/digital-agriculture/en/) | 数字农业服务、数据和农户可达性 | 以本地语言、低门槛输入和可解释结果服务真实农户 |
| [Ragas](https://arxiv.org/abs/2309.15217) | 分离评估检索相关性、忠实度和回答质量 | 为每个场景建立离线评测集，不能只看回答是否流畅 |

### 研究判断

竞品大致分成三类：视觉诊断工具、传感器/农场管理工具、通用农技助手。CropWise 不应正面复制它们的硬件或大规模数据资产，首个差异化楔子应是：

> **场景入口 → 结构化现场简报 → RAG 证据 → 五段式决策卡 → 复查节点 → 人工升级。**

这条链路可以利用现有的农业知识库、流式 UI、来源卡片和会话记忆，形成可持续积累的病例数据。

## 2. 当前交付范围

### 已实现：场景化提问入口

首页“选择农业场景”支持四种场景：

1. **病虫害诊断**：作物、地区、生育期、症状与扩散。
2. **施肥灌溉**：作物、地区、生育期、目标或异常。
3. **农时计划**：作物、地区、当前农时、计划目标。
4. **政策核验**：涉及作物/项目、地区、政策主题、需要核验的事项。

不同场景会生成不同的提问协议，并要求回答继续使用“现场摘要、优先判断、现在做什么、风险边界、复查节点”五段式决策卡。

### 下一阶段：决策事件时间线

在不改变当前聊天接口的前提下，为每个 `thread_id` 增加农业事件：

```json
{
  "case_id": "case_01",
  "thread_id": "thread_01",
  "scenario": "diagnosis",
  "crop": "水稻",
  "region": "江西南昌",
  "stage": "分蘖期",
  "observations": ["叶尖发黄"],
  "actions": [{"text": "检查水层和根系", "due_at": "2026-08-11"}],
  "review": {"status": "pending", "result": null},
  "created_at": "2026-08-09T10:00:00+08:00"
}
```

## 3. 用户工作流

### 病虫害诊断

1. 选择“病虫害诊断”。
2. 填写作物、地区、生育期、症状和扩散范围。
3. 系统检索知识库，输出 2-3 个可能方向及依据。
4. 用户查看“现在做什么”和风险边界。
5. 用户在 24-72 小时后提交复查结果，系统更新病例状态。

### 施肥灌溉

输入目标产量、叶色/墒情、最近施肥和天气；输出时必须区分“建议时机”和“建议用量”，并提醒测土、品种、肥料登记和安全间隔。

### 农时计划

输入地区、作物、当前农时和目标日期；输出按日期排序的任务、前置条件和天气风险。日期必须来自工具或官方数据，不能由模型凭空生成。

### 政策核验

输入政策主题、地区和需要确认的事项；优先给出农业农村部、江西省农业农村厅、地方政府等官方链接，并明确“已核验 / 待人工确认”。

## 4. 技术设计

### SSE 事件协议

现有协议继续兼容，并新增：

```json
{
  "type": "ui",
  "component": "decision-card",
  "props": {
    "summary": "现场摘要文本",
    "judgments": ["可能方向及依据"],
    "actions": ["现在可以执行的动作"],
    "risks": ["安全边界和升级条件"],
    "followup": ["复查时间和观察指标"],
    "complete": true
  }
}
```

### 后端模块边界

- `domain_guard.py`：农业范围与安全边界。
- `knowledge_base.py`：向量检索、元数据和召回评估。
- `agent.py`：场景提示词、工具循环、决策卡抽取和 SSE 事件。
- `memory.py`：会话历史与后续农业事件记录。
- `tools.py`：农时、官方资料、开放图片和天气等工具。

不要把场景逻辑写成前端字符串判断的唯一来源；后端应接收结构化 `scenario_context`，前端生成的文本只作为兼容回退。

### 建议 API

```text
POST /cases                       创建农业案例
GET  /cases?thread_id=...         查询会话案例
GET  /cases/{case_id}             查看案例时间线
POST /cases/{case_id}/review      提交复查结果
POST /cases/{case_id}/escalate    转交农技人员
GET  /knowledge-base/search       诊断召回质量
```

## 5. 数据与隐私原则

- 默认只保存用户主动提交的作物、地区和观察内容。
- 地块位置精度默认到县/区，不强制保存精确坐标。
- 图片和病例需要明确保留期限与删除入口。
- 农药、肥料和政策回答保存来源、时间和模型版本，支持追溯。
- 人工升级前显示将要共享的字段，避免隐私无感外传。

## 6. 评测与验收

### 离线评测集

每个场景先建立 25 条人工标注问题，总计至少 100 条，字段包括：

- 场景分类准确率；
- 召回文档相关性；
- 回答对证据的忠实度；
- 五段式完整率；
- 农药/肥料安全提醒覆盖率；
- 非农业越界率；
- 复查节点可执行性。

### MVP 验收标准

- 四种场景都能生成不同的结构化提问；
- 决策卡 SSE 事件在流式结束前到达；
- 缺失现场信息时显示待补充，而非生成虚构事实；
- 旧 Markdown 回答仍能正常显示；
- 移动端无横向滚动，所有操作目标不少于 44px；
- 生产构建和核心路由通过；
- 诊断、施肥、农时、政策各有至少 10 条回归测试问题。

## 7. 90 天路线

### 第 1-2 周：场景入口与评测

- 完成结构化 `scenario_context` 请求字段；
- 建立四类场景评测集；
- 决策卡增加引用来源和模型/知识库版本。

### 第 3-6 周：病例时间线

- `cases` 和 `case_events` 数据表；
- 复查提醒和处理结果；
- 失败/无效建议反馈入口。

### 第 7-10 周：区域与官方数据

- 江西县域农时日历；
- 农业气象和官方政策检索；
- 图片辅助鉴别与人工升级。

### 第 11-13 周：小范围试用

- 邀请江农师生、农技人员和种植户试用；
- 比较自由提问与场景入口的完成率、采纳率和复查率；
- 按真实失败案例调整知识库和提示词。

## 8. 当前版本的产品原则

CropWise 的优势不在于给出最长的回答，而在于让用户知道：

1. 我们对现场了解了什么；
2. 哪些判断有知识依据；
3. 今天应该做什么；
4. 哪些风险不能由 AI 代替确认；
5. 什么时候回来告诉系统结果。
