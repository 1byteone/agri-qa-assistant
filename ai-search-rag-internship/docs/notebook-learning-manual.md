# Notebook 项目驱动学习手册

这份手册解决一个常见问题：Notebook 能运行，不代表学习真的发生了。真正的学习结果应该是：你能从现象推回原理，能用实验支持工程决策，能把阶段产物接到最终产品，而不是只会复制一个代码单元格。

## 一、总目标：八周交付一个可解释的 Mini RAG

这次学习以 **Evidence Quest / 证据侦探社** 为主线。你不是完成一堆互不相干的练习，而是连续处理一宗案件：为真实观众找到资料、解释排名、证明速度和质量，最后交付一个带引用的证据工作台。每个阶段的知识只在作品需要它时出现。

最终项目是 EvidenceDesk Mini RAG：

```text
PDF/Markdown
  -> 解析和页码元数据
  -> 中文 Recursive Splitter
  -> 稳定 Chunk ID
  -> BM25 baseline / 可选 Dense + Hybrid
  -> qrels 质量评估
  -> 延迟与资源 Benchmark
  -> FastAPI /search /chat
  -> 带 source/page/chunk_id 的引用
```

每个阶段不是一个孤立练习：

| 阶段 | 要解决的真实问题 | 阶段产物 | 产物如何进入下一阶段 |
| --- | --- | --- | --- |
| Phase 1 | 原始文件如何变成可追溯文本？ | `data/processed/chunks.json` | Phase 2 直接读取并建立索引 |
| Phase 2 | 如何找到最相关的 Chunk？ | BM25、qrels、Recall/MRR | Phase 3 对同一检索链路测性能 |
| Phase 3 | 更快是否牺牲了质量？ | benchmark 表、错误归因 | Phase 4 采用经过验证的配置 |
| Phase 4 | 如何让别人可靠使用？ | API、测试、引用 Demo | README 和面试演示 |

## 二、每次学习的固定循环

每个 Notebook 都按以下顺序运行。不要一次性执行后只看最后输出。

每课开头的任务卡会写明：你的身份、案件背景、专业 Goal、展示作品和通关判定。末尾的 Boss Challenge 是故意保持注释的代码模板，适合先遮住答案自己写，再逐行取消注释验证。

### 1. 先读目标

回答：今天要改变项目中的哪个真实能力？如果删掉今天的代码，最终系统会失去什么？

### 2. 先做直觉实验

用很小的数据或二维向量观察现象。例如：先用 2D cosine 理解 Dense，再考虑 BGE-M3；先看 overlap 如何复制边界，再讨论更复杂的切分器。

### 3. 再读项目实现

把直觉实验中的变量对应到代码：`chunk_size`、`overlap`、`k1`、`b`、`top_k`、`rrf_k`。每个参数都要能回答“它改变了什么”。

### 4. 只改变一个主要变量

如果同时改变模型、分块大小、top-k 和 tokenizer，你无法判断结果来自谁。实验记录至少写：baseline、改变的变量、观察、解释、下一步。

### 5. 写出工程结论

结论必须包含范围：

> 在数据版本 X、参数 Y、硬件 Z、Query 集 Q 上，观察到指标 A 从……变为……；这说明……，但还不能证明……。

## 三、Phase 1：从文件到 Chunk

### 必须会到什么程度

- 能使用 `Path` 遍历目录并区分支持/不支持的文件。
- 能解释 UTF-8、`strip`、字符串切片对文本内容的影响。
- 能看懂 `dataclass`，知道为什么用统一的 `ParsedDocument` 而不是到处传字典。
- 能说明 `source/page/metadata` 为什么属于数据契约。

### 为什么先解析再分块

解析负责回答“原文是什么、来自哪里”；分块负责回答“检索时以多大单位返回”。两者混在一起会导致后续无法判断问题来自 PDF 提取还是边界策略。

### 必做实验

1. 比较 Markdown、TXT、PDF 的统一输出。
2. 用不同分隔符观察递归降级过程。
3. 固定 `chunk_size`，只改变 overlap，记录 Chunk 数和最大长度。
4. 重复运行，验证稳定 ID。
5. 故意传入非法 overlap 和不支持扩展名，观察错误。

### 完成标准

输出能被 JSON 读取；每条 Chunk 有稳定 ID、文本、source、page；长度约束通过；你能解释一次边界选择。只打印 Chunk 数不能算完成。

## 四、Phase 2：从关键词到 Hybrid

### 必须会到什么程度

- 能把 Query 和结果看成有顺序的 ID 列表。
- 能解释 TF、IDF、长度归一化和中文 tokenizer 的取舍。
- 能用一个二维例子计算 cosine 的含义。
- 能手算一个 Recall@k 和 MRR@k。
- 能解释 RRF 为什么不比较 BM25 和 cosine 的原始分数。

### 为什么先做 BM25

BM25 是可解释 baseline。它让你先知道“精确词匹配能做到什么”，之后 Dense 或 Hybrid 的任何提升都有参照。如果一开始只接入黑盒模型，出现错误时你无法判断是数据、切分、模型还是评估的问题。

### 必做实验

1. 查看中文字符级 tokenization 的结果。
2. 用稀有词和常见词对比 IDF。
3. 在真实 `chunks.json` 上运行 BM25。
4. 用二维向量模拟 Dense 排名，明确这是机制实验而不是模型成绩。
5. 对同一组排名运行 RRF，观察两路共同出现的文档如何获益。
6. 用 qrels 计算 Recall/MRR，记录一个误召回并解释原因。

### 完成标准

你能独立画出 BM25-only、Dense-only、Hybrid 的数据流，并且知道当前仓库真实运行的是哪一条。没有真实 Dense 依赖时，必须在报告中明确标注，不得把模拟结果写成 BGE-M3 指标。

## 五、Phase 3：从“感觉快”到可复现 Benchmark

### 必须会到什么程度

- 知道 warmup 和冷启动是不同测量对象。
- 能解释 mean、P50、P95，不把 P95 当成“95 次平均”。
- 能固定输入和环境，只改变一个变量。
- 能把质量指标和延迟指标放在同一张表。
- 能将失败归因到解析、召回、上下文、生成或评估层。

### 为什么速度不能单独成为结论

一个系统可以把 top-k 从 10 降到 1，变得更快，但漏掉更多证据；也可以返回很多重复 Chunk，让 Recall 看似提高但上下文噪声变大。性能优化必须回答：快了多少、质量损失多少、在什么输入规模和硬件上成立。

### 必做实验

1. 比较第一次查询和 warmup 后的稳定查询。
2. 用固定迭代测 mean/P50/P95。
3. 改变 top-k，同时观察 latency 和 qrels 质量。
4. 改变 chunk 参数，观察索引规模、质量和延迟。
5. 检查 ONNX/INT8 依赖；没有真实导出时不要伪造结果。
6. 为三类失败样本写“现象 → 归因 → 下一步只改变什么”。

### 完成标准

任何一条性能数字都能追溯到数据、参数、设备和测量方法；你能说明它的适用边界；报告中同时有速度和质量。

## 六、Phase 4：从脚本到产品

### 必须会到什么程度

- 能区分请求、响应、状态码和服务内部对象。
- 能解释 Pydantic 为什么拒绝非法输入。
- 能用 TestClient 验证 API 合同，不依赖手工点击。
- 能说明索引为什么应该复用，而不是每次请求重建。
- 能解释 evidence-only fallback 如何降低无证据生成风险。

### 为什么引用是核心功能

用户不只需要一段听起来合理的文字，还需要回到原文验证。`chunk_id/source/page/score/index_version` 让回答可追溯、可调试、可评估；它们不是“以后再加的日志字段”。

### 必做实验

1. 先调用 `/health`，确认索引版本和 Chunk 数。
2. 调用 `/search`，检查每个结果的引用字段。
3. 无 API Key 调用 `/chat`，确认是 evidence-only。
4. 测试空 Query、无结果、错误目录和合法 source filter。
5. 用 TestClient 写用户故事级断言。
6. 保存一次 Demo 记录，包含 Query、模式、索引版本和 citations。

### 完成标准

别人按 README 能启动；服务在没有外部模型时仍可检索；错误输入有明确响应；每个答案都返回引用；测试保护关键合同。

## 七、每阶段复盘卡

完成一个阶段后，在对应报告或 Notebook 最后补齐：

```text
本阶段要解决的用户问题：
我选择的 baseline：
本次只改变的变量：
最重要的观察：
我对观察的原理解释：
支持解释的代码/指标：
失败样本：
当前不能声称什么：
下一阶段会复用的产物：
简历可写的一句话：
```

## 八、最终面试级验收

你不需要把所有高级技术都接入才算完成，但必须能诚实回答：

1. 为什么当前版本选择 BM25 baseline？
2. 什么时候 Dense 或 Hybrid 值得引入？
3. Chunk 参数是如何通过实验选择的？
4. 你如何证明优化没有悄悄损害 Recall？
5. 如果 LLM 编造了不存在的事实，你从哪一层开始排查？
6. 用户如何从回答回到原文？

能用 Notebook 的代码、输出和报告逐项回答，才是“知其然，更知其所以然”。
